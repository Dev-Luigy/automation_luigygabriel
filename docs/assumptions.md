# Assumptions register

Assumptions are explicit because the assignment intentionally leaves important
behavior undefined. An assumption may be revised after stakeholder feedback,
but its history should remain traceable.

| ID | Assumption | Status | Rationale or follow-up |
| --- | --- | --- | --- |
| A-001 | The service processes BRL only. | accepted | The input field and policy thresholds are explicitly BRL. |
| A-002 | Money enters the domain as exact `Decimal`, never `float`. | accepted | Required for deterministic financial comparisons. |
| A-003 | Submission timestamps use timezone-aware ISO 8601. | accepted | The sample uses a UTC `Z` timestamp. |
| A-004 | Receipt dates in Portuguese OCR use `DD/MM/YYYY`. | accepted and implemented for assessment | Matches the sample; missing, invalid, or ambiguous dates cannot auto-approve. Production must confirm accepted locale/formats. |
| A-005 | Receipt calendar dates are interpreted in `America/Sao_Paulo`. | accepted and implemented for assessment | The business context is Brazil; production policy still must formally own the timezone. |
| A-006 | Exactly 90 days old is valid; only more than 90 days is rejected. | accepted and implemented | The requirement says "more than 90 days"; acceptance tests cover the boundary. |
| A-007 | Exactly BRL 200 may be auto-approved when every check passes. | accepted | The requirement says "BRL 200 or less." |
| A-008 | BRL 200.01 through BRL 2,000 goes to human review. | implemented assessment interpretation; stakeholder validation open | The baseline does not authorize auto-approval above BRL 200, but the assignment does not fully define the intermediate band. |
| A-009 | Exactly BRL 2,000 is not in the "above BRL 2,000" gate but still requires review under A-008. | implemented assessment interpretation; stakeholder validation open | Literal threshold interpretation covered by tests, not confirmation of production policy. |
| A-010 | An explicit rejection rule has precedence over the high-value review gate. | superseded by A-056 and policy v3 | The literal `> BRL 2,000` review gate is now non-bypassable; deterministic reject evidence constrains the later human outcome to rejection. |
| A-011 | Amount or category disagreement routes to review rather than automatic rejection. | accepted and implemented | The discrepancy may be extraction or employee error and requires judgment. |
| A-012 | The assessment receives `raw_ocr_text`; binary OCR processing is a separate adapter. | accepted assessment boundary; production blocker | It follows the assignment object, but self-attested text cannot safely authorize real money without application-owned bytes/checksum and trusted OCR. |
| A-013 | Human decisions are authoritative only when written through the service. | accepted | Required for internal auditability. |
| A-014 | Production reviewer identity comes from corporate OIDC/SSO. | superseded | The user explicitly rejected dependency on existing RecargaPay systems; see D-035. |
| A-015 | The assessment uses HTTP Basic with PBKDF2 password hashes; production replaces it with application-owned managed OIDC. | accepted for assessment | Authentication is an adapter; reviewer identity remains server-derived. |
| A-016 | No external task manager or messaging integration is included in the MVP. | accepted | Human review lives entirely inside the service. |
| A-017 | The old integration-only SQLite schema is replaced by internal reimbursement, review, decision, idempotency, audit, and application-metadata persistence. | accepted and implemented | The current schema includes workflow, lease/recovery, operational-audit, and decision-command idempotency records. |
| A-018 | A second LLM does not automatically establish near-zero error. | accepted | Accuracy must be measured on labeled representative data. |
| A-019 | Submitter/reviewer UIs, binary upload, downloads, and JSON endpoints share one origin. | accepted and implemented | Avoids CORS and simplifies origin, CSRF, and credential controls. |
| A-020 | TLS terminates at the application or a trusted reverse proxy in production. | accepted | Local development may explicitly allow HTTP. |
| A-021 | Reviewers have modern browsers with JavaScript enabled. | validated for assessment; production confirmation required | The implemented screen and browser test use modern DOM, `fetch`, modules, and `dialog`. |
| A-022 | The assessment stores and displays attachment locations but does not provide content access. | superseded by A-058 | Local managed evidence upload and authorized access exist; production S3 versioning, scanning, OCR binding, uploader ownership, and retention remain open. |
| A-023 | File-backed SQLite and a single service instance are sufficient for assessment validation. | accepted for assessment | Production datastore, HA, throughput, backup, and recovery requirements are unknown. |
| A-024 | Raw OCR text is necessary reviewer evidence, while the raw model response should remain outside the browser response. | accepted | Structured facts and safe trace metadata are sufficient for the current reviewer UI; the complete response remains persisted for audit. |
| A-025 | A trusted production ingress terminates TLS and is the only source trusted for forwarded headers. | accepted architecture assumption | The standalone deployment must provision and record its ingress CIDRs, certificates, and proxy-header standard. |
| A-026 | Reviewer credentials may be startup configuration for the assessment; reviewer/session tables are unnecessary in this slice. | accepted for assessment | Production replaces this with standalone managed OIDC, authorization, revocation, and access governance. |
| A-027 | Correlation IDs are supplied by the authoritative upstream processing context. | proposed for production | The persistence boundary propagates a supplied ID; its derived fallback is intended only for the demo/helper path. |
| A-028 | No n8n/Linux/local-model environment is part of the standalone baseline. | accepted planning constraint | Do not make the assessment depend on a pre-existing automation platform; reconsider n8n only as a deliberately owned peripheral after its execution, identity, network, secret, audit, and support boundaries are approved. |
| A-029 | AWS `sa-east-1` is used only as the standalone production and pricing reference. | study assumption | The final owned account structure, approved region, data residency, and commercial discounts still require an explicit deployment decision. |
| A-030 | Cost scenarios use 1M and 10M cases per month, three API/Lambda/SQS operations, 2.25 Lambda GB-seconds, 1 MB retained per case, and illustrative 90-day retention. | cost-model assumption | These values are sensitivities, not a traffic forecast or retention decision. |
| A-031 | Lambda latency is acceptable for the study when OCR/LLM processing is asynchronous. | user-provided study assumption | Production still needs P95/P99 SLOs, cold-start tests, and provisioned-concurrency analysis. |
| A-032 | No production receipt-retention or deletion period is currently authorized. | accepted planning constraint | Legal, Privacy, Finance, Data Governance, Security, and the accountable owner must approve the matrix before lifecycle expiration. |
| A-033 | No VPN or private-network-only reviewer requirement is currently known. | open | Use managed OIDC and private data stores by default; make the standalone product security/network decision from its threat model. |
| A-034 | Aurora capacity, storage, and I/O figures in the cost study are modeling assumptions. | cost-model assumption | Replace them with load-test and production telemetry before procurement. |
| A-035 | RecargaPay has, or will nominate, a corporate OIDC-compatible identity authority for reviewers. | superseded | Standalone deployment must own its identity service; see D-035. |
| A-036 | Employees already use a RecargaPay-owned channel that can submit reimbursements and display sanitized status/results. | rejected by user | The standalone product must implement its own submitter upload and tracking interface. |
| A-037 | The three initial presentation locales are `pt-BR`, `en`, and `es`, with stable nonlocalized API codes. | accepted | Confirm translation ownership and whether Spanish needs a regional variant before production content approval. |
| A-038 | Production queue navigation must remain usable with millions of cases without sending an unbounded collection to the browser. | accepted | Use bounded server-side search/filter/sort, keyset pagination, maintained metrics, and load tests against representative cardinality and skew. |
| A-039 | Searching for a request must operate over the entire authorized server-side scope, not only the current browser page. | accepted; pending search and exact all-status lookup implemented, history/audit search planned | The indexed queue covers pending cases across cursor pages, and `GET /api/requests/{request_id}` provides exact lookup across every retained status. A dedicated completed-case explorer, saved views, and cross-case audit search remain unimplemented; retain keyset navigation rather than high-offset numeric page jumps. |
| A-040 | Reviewers require protected on-demand access to the exact original evidence and a sanitized business timeline, while technical trace remains separately authorized. | accepted and locally implemented; production controls partial | Detail exposes managed original bytes only through an authenticated case-scoped route and records the access. SHA-256/media are revalidated on reads and again before a decision. S3 object version, quarantine/malware state, OCR binding, privileged trace search, and approved retention remain production work. |
| A-041 | Every OCR/model stage, retry, and reprocessing attempt needs its own immutable trace record. | accepted and storage implemented; orchestration partial | `processing_invocation_attempts` is 1:N by run/stage/attempt and terminal rows are immutable. The current synchronous service uses one primary attempt; retry/reprocessing orchestration and chained multi-stage inputs remain production work. |
| A-042 | Every configured assessment reviewer currently has the same global case/timeline/decision scope. | superseded by A-059 | Explicit submitter/reviewer/auditor/admin capabilities, owner result reads, and self-review denial are implemented. Team, tenant, case assignment, value and purpose predicates remain absent. |
| A-043 | The CloudFront/S3/API Gateway/Lambda/SQS/Aurora/Cognito topology is the accepted production deployment target, but `sa-east-1` and its account/network layout remain planning assumptions. | accepted target; implementation and regional validation pending | The user confirmed AWS serverless. Region, data residency, provider availability, RPO/RTO, account separation, peak load, and enterprise pricing still require accountable approval and tests; the assessment SAM package is not this production target and no cloud resource was provisioned. |
| A-044 | The production browser receives only an opaque BFF session cookie, while provider tokens stay server-side. | accepted target; implementation pending | Cognito authenticates through Authorization Code with PKCE; DynamoDB stores a hashed, revocable session record. The API derives the actor and applies application/SQL authorization. No token or internal reviewer ID is entered or persisted by browser JavaScript. |
| A-045 | DynamoDB TTL is session-storage cleanup, not the authorization expiry mechanism. | accepted security invariant | TTL deletion may be delayed. Every authorizer call must validate absolute/idle expiry, status, and revocation synchronously, and authorization caching must satisfy the revocation SLO. |
| A-046 | Production business events need a monotonic per-case aggregate sequence in addition to occurrence and recording timestamps. | accepted production requirement | Delayed asynchronous events can have timestamps that do not match commit order. Timeline keyset cursors should use immutable sequence plus event ID and a snapshot maximum; source occurrence time remains evidence rather than the sole ordering authority. |
| A-047 | Any Kubernetes comparison assumes an application-owned standalone EKS platform; no existing RecargaPay cluster, shared capacity, or platform team is available. | accepted planning constraint | Price and own the control plane, workers or Fargate capacity, ingress, upgrades, autoscaling, observability, security, recovery, and on-call operation. Revisit only with explicit infrastructure evidence. |
| A-048 | “Finish the project” means complete the Python GitHub code-assessment deliverable, not provision the documented AWS production topology. | accepted delivery boundary | The repository contains the end-to-end assessment path, instructions, tests, design and report. A later explicit request added non-production sandbox IaC, but did not authorize a live cloud mutation or redefine the production completion gate. |
| A-049 | The assignment's caller-supplied `submitted_at` may anchor the assessment's 90-day rule, but not a production financial rule. | accepted assessment boundary; production blocker | Production must add server-owned `received_at` or separate claimed/authoritative timestamps and define clock/timezone ownership before monetary use. |
| A-050 | Caller-supplied `raw_ocr_text` is sufficient to exercise extraction/policy in the assessment, but cannot be trusted evidence for auto-approval in production. | accepted assessment boundary; production blocker | Production must bind trusted OCR to exact application-owned receipt bytes, object version/checksum, validated media, and malware state. |
| A-051 | Server-derived HTTP Basic identity demonstrates attribution but not authorization. | partially superseded by A-059 | Configured roles and owner/self-review checks now authorize the assessment. Managed identity lifecycle and richer RBAC/ABAC remain production blockers. |
| A-052 | A durable running processing state without automated recovery is acceptable only for the synchronous assessment. | superseded by A-060 | Retry-triggered five-minute lease recovery now appends abandonment/resume evidence and fences stale workers; background supervision and queue/DLQ controls remain absent. |
| A-053 | Current audit coverage proves processing and decision history, not every service operation. | partially superseded by A-061 | Every HTTP attempt now receives a sanitized operational record. Transactional outbox, query-context policy, cross-case search/export, and approved off-host WORM retention remain production blockers. |
| A-054 | The user reports approximately 10 hours of total project effort; the measured 40m 29s completion block is included in that estimate, not additional. | user-reported estimate | The rough total must not be decomposed into fabricated historical durations. The later AWS packaging work remains inside the user's rough reporting value rather than receiving reconstructed timestamps. |
| A-055 | “Plug and play on Amazon” means provide locally validated, one-command IaC for a synthetic assessment sandbox, not provision an account or claim the accepted production stack exists. | accepted implementation boundary | SAM defaults to `sa-east-1` and packages API Gateway/Lambda/VPC/EFS with one interactive admin, a distinct synthetic seed actor, SQLite, and managed EFS evidence. No AWS resource was provisioned. SQLite/EFS, bounded concurrency, direct `execute-api`, minimal account model, and missing production adapters forbid real financial data. |
| A-056 | Claims above BRL 2,000 must always reach human review, even when another rule mandates rejection. | accepted and implemented | A reject evaluation remains visible and forbids human approval; the reviewer confirms rejection with rationale. |
| A-057 | Missing receipt evidence must prevent automatic approval. | accepted and implemented | Empty evidence routes to review under `baseline-v3`; public HTTP intake accepts only verified managed references. |
| A-058 | Local immutable filesystem envelopes are sufficient only for assessment evidence. | accepted assessment boundary | Exact bytes, filename, MIME, size, and SHA-256 are protected locally; malware scan, uploader ownership, OCR binding, S3 versioning, lifecycle, and legal hold are absent. |
| A-059 | Configuration-backed roles plus owner checks and actor-bound self-review denial are sufficient for the assessment. | accepted assessment boundary | `ReviewService` compares the authenticated intake actor and reviewer and fails closed when legacy authorship is unknown. Production still requires managed identity lifecycle and durable team/tenant/assignment/value/purpose authorization. |
| A-060 | A five-minute lease recovered by an identical retry is sufficient to demonstrate crash recovery. | accepted assessment boundary | No heartbeat, watchdog, retry cap, backoff, operator replay, SQS, or DLQ exists; a long provider call may execute twice but cannot persist a second decision. |
| A-061 | A privacy-bounded operational row for every HTTP attempt satisfies local assessment observability. | accepted assessment boundary | It omits body/query values and is stored in a separate SQLite transaction; production requires an outbox, approved immutable archive, access controls, and audit search/export. |
| A-062 | A synchronous trilingual upload-and-track portal is sufficient for the standalone assessment. | accepted and implemented | Production should use direct object upload and asynchronous processing for scale; completed-case browsing and audit administration remain separate surfaces. |
| A-063 | Human decision retries require a durable command key in addition to aggregate version control. | accepted and implemented | Key hash plus command fingerprint is written atomically with the decision; exact retry replays, divergent reuse conflicts. |
| A-064 | Approval must revalidate the original at the instant of human decision. | accepted and implemented | Queue residence can outlive intake verification. Missing/corrupt/unverifiable evidence can support only a reasoned rejection, whose integrity state is audited. |
| A-065 | A build ID plus SHA-256 of effective configuration is the minimum executable identity for assessment reproducibility. | accepted and implemented | Provider/prompt/policy hashes alone cannot identify deployed code and settings. Secrets contribute to the in-memory digest but are never persisted in cleartext. |
| A-066 | Browser-generated request IDs need at least 128 bits of randomness for the stated million-request scenario. | accepted and implemented | The previous 32-bit suffix had unacceptable birthday-collision probability; backend fingerprint conflicts remain authoritative. |
| A-067 | `transportation` is the canonical transport category code. | accepted and implemented | It matches extractor/sample output; `transport` remains a display-only legacy alias. |
| A-068 | Equal receipt bytes under different request IDs are a risk signal, not sufficient proof of fraud. | proposed production policy | Persist object checksum/version reuse and combine it with merchant/date/amount/actor/window before routing `POSSIBLE_DUPLICATE_RECEIPT` to review. No automatic rejection is authorized. |
| A-069 | The minimal AWS sandbox needs only one interactive operator because its three review cases are submitted by a distinct seed actor. | accepted assessment boundary | A request newly submitted by that admin cannot be self-reviewed; multi-operator demonstrations require additional credentials and production requires managed account lifecycle. |
